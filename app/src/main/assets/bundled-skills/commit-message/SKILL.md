# 提交信息

读者是三个月后的你和 release 脚本。标题回答「做了什么」，正文回答「为什么这么做、还有什么后果」。

## 格式

```
<type>(<scope>): <一句话，动词开头>

<为什么需要这个改动；之前的行为是什么，坏在哪>
<选了这个方案的取舍；被放弃的方案一句话理由>

<关联 issue / 破坏性变更说明>
```

type 取值：`feat` `fix` `perf` `refactor` `docs` `test` `build` `ci` `chore`。
scope 用模块名（`engine`、`plugins`、`runtime`），没有明确模块就省略。标题控制在 60 字内。

## 正文写什么

- **因果**：「因为 X 会在 Y 条件下重入，所以把锁挪到 Z」。不写「优化了代码」「修复了一些问题」。
- **取舍**：两条路都行时的选择理由，一段话以内。
- **影响面**：存储格式、协议字段、默认行为变更必须写明，读者要据此决定是否迁移。
- **验证**：贴一行真跑过的命令，比如 `node test/skill-manager.test.mjs → 10 pass`。

## 不写什么

- 过程流水账（先试了 A，又试了 B），除非结论依赖它。
- 「按需求修改」——需求是什么得写出来。
- 无信息量的 emoji、`update`、`fix bug` 这类标题。

## 破坏性变更

标题后加 `!`（`feat(api)!: 收窄 install 回包`），正文第一段写迁移方式：旧调用怎么改、默认值怎么给、有没有兼容窗口。

## 拆分

一个提交一件事。判断标准：能不能单独回滚而不牵连其他改动。探测性提交、格式化、依赖升级各自独立。

出处：基于 Conventional Commits 规范与 obra/superpowers 的工作流约定改写。
