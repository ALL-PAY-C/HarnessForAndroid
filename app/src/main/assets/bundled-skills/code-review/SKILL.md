# 变更审查

目标不是表态，是找出「合进去之后会出事」的地方。读代码不是读全文，是先建立意图模型再对着 diff 验证。

## 步骤

1. **先读为什么**：commit message / PR 描述 / 关联 issue。没有就写「意图不明」并停在这里——猜意图去审是白审。
2. **只看 diff 的上下文窗口**：每个 hunk 往上往下各读 20 行，搞清楚它改的那个不变量原来靠什么维持。
3. **按风险排序，不按文件顺序**：命中这几类先看——
   - 并发 / 生命周期 / 缓存失效
   - 错误路径：throw、catch 吞掉、返回 null 或空集合
   - 边界：空输入、单元素、超长、重复调用
   - 资源：文件、socket、游标、订阅有没有成对释放
   - 兼容：回包字段、协议、存储格式变更有没有跟着迁移
4. **能验证就验证，别靠眼力**：跑测试、跑 repro、写一个断言脚本。跑不动的说明「未验证」。
5. **给结论，分三档**：必须改（会坏）、建议改（会疼）、可以不改（风格）。每条带 `文件:行号` 和一句话改法。

## 反模式

- 用「这里是不是可以更优雅」占满结论——那是最后一档。
- 复述 diff 做了什么（作者自己知道）。
- 提了问题却没给下一步。
- 因为改动大就笼统说「建议拆小」——除非能指出具体哪两个关注点搅在一起。

## 输出格式

```
必须改
- path/file.kt:142 catch 吞掉 IOException，磁盘满时静默丢数据 → 至少记日志 + 上抛
建议改
- path/other.kt:88 循环里 join 路径，O(n^2) → 提到循环外
可以不改
- 命名 x2 → itemCount
```
