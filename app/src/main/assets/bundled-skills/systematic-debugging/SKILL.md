# 系统化调试

调试失败几乎都源于同一个动作：在没复现的情况下开始改代码。顺序不能跳。

## 1 复现

- 写出**最短**复现步骤或一条命令，成功标准是「每次都能看到同一个错误」。
- 复现不出来就先补证据（日志、断点、抓包、最小输入），不要开始猜。
- 偶发问题记频率和条件（并发、时间、数据量），它是线索不是障碍。

## 2 建立基线

- 拿到**确切**错误信息：类型、消息、栈帧、发生位置。别用「好像抛了个异常」推进。
- 确认这份代码就是跑起来的那份（构建产物、缓存、旧进程是最常见的假故障）。
- 记下当前失败率或耗时，改完要拿它对比，否则「应该好了」不算好了。

## 3 二分定位

在数据流上切一刀，判断错误在刀的哪一侧：

- 输入侧还是输出侧（在函数入口打一行日志就能分）。
- 上游还是下游（上游 mock 掉、下游喂固定值）。
- 哪个提交引入：`git bisect run <复现命令>` 是自动化的，别手试。
- 哪份配置或环境差异（同代码两个环境一个坏一个好，直接 diff 环境）。

每切一刀把范围缩小一半，最多 10 次就能从 1000 行定位到 1 行。

## 4 单假设验证

- 一次只改一个变量，改完立刻跑复现命令。
- 假设被证伪就明确记下来（写下「不是 X，因为 Y」），否则会绕回来重试同一个错误。
- 找到根因再动手：改症状不叫修，叫欠债。

## 5 收尾

- 补一个**会因为这个 bug 而失败**的测试，跑一遍确认它在改前红、改后绿。
- 在根因处留一行注释解释「为什么必须这样写」——只写为什么，不写发生了什么。
- 同一个根因的其他调用点一起修（grep 调用方，改共享入口）。

## 卡住时

写下你**确定知道的三件事**和**正在假设的一件事**。假设为空就是缺证据，回去加观测；证据齐了还不动，就是拆分粒度不够，继续二分。
