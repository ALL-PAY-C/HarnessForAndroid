# 测试先行

测试先行不是流程洁癖，它的唯一目的是**先确定验收条件**，避免用实现倒推「什么算对」。

## 红

1. 用一句人话写下要保证的行为：「给定 A，当 B，那么 C」。
2. 先写测试，断言 C。此时**必须运行并看到它失败**，失败原因要能读懂（不是编译错误、不是路径错）。
3. 一个测试只钉一个行为。名字写成句子：`安装同名技能时覆盖旧内容`。

## 绿

4. 写**刚好够**让测试通过的实现。可以丑，可以先特判，只要能过。
5. 全量测试跑一遍，确认没有把别的东西弄红。新增的红必须当场处理：改实现或改测试，不能搁置。

## 重构

6. 在绿的状态下动结构：抽函数、改名、去重、分层。行为不变，测试必须保持绿。
7. 每步小重构后立刻重跑，别攒一大坨再跑。

## 该测什么

- 契约边界：空输入、单元素、超长、重复调用、错误路径。
- 曾经出过 bug 的地方（回归测试的性价比最高）。
- 有分支的判断逻辑（if/else、权限、状态机迁移）。
- **不测**：getter、纯转发、框架本身、只为覆盖率而写的断言。

## 测试本身的坏味道

| 现象 | 原因 | 改法 |
| --- | --- | --- |
| 一改实现测试就红 | 测了实现细节 | 断言可观察结果，不断言内部调用 |
| 只能跑一次 | 共享了状态 | 每个用例自建临时目录并清理 |
| 失败信息看不懂 | 断言太笼统 | 断言里带实际值与期望值 |
| 跑得慢 | 引了真网络或真时钟 | 注入时间与 IO，网络只留一个烟测 |

## 纪律

- 不许跳过失败测试（skip / xfail）来「先合进去」。
- 不许为了让测试过而改断言——除非你确认原来的断言写错了，并在提交信息里说清。
- 没跑就说没跑。
