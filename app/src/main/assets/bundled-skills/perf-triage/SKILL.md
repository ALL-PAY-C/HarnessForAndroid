# 性能排查

没有度量就没有优化，只有猜测。固定顺序：量 → 定位 → 改一处 → 同口径复测。

## 1 定义口径

- 指标是什么：端到端耗时、吞吐、内存峰值、首帧时间、GC 次数。一次只盯一个主指标。
- 环境固定：设备或 CPU、数据规模、冷热启动、debug 还是 release。换环境就没法对比。
- 记下当前数值作为基线，之后每次改动都跟它比。

## 2 先分清等待与计算

| 症状 | 多半是 | 先查 |
| --- | --- | --- |
| CPU 打满、耗时随数据量线性涨 | 计算 | 热点函数、循环嵌套、重复解析 |
| CPU 不高但慢 | 等待 | IO、锁、网络、序列化、跨进程 |
| 越跑越慢 | 泄漏 | 集合只增不减、监听器未注销、缓存无上限 |
| 抖动大 | 调度或 GC | 大对象分配、频繁字符串拼接、线程争用 |

## 3 定位热点

- 有 profiler 就用 profiler，别靠读代码猜热点——直觉错得很有规律。
- 没有 profiler 就二分：把可疑阶段各打一行时间戳，一次去掉一半。
- 只看占比前 3 的热点，剩下的先不管（通常 80% 时间在 3 个地方）。

## 4 改一处，复测

- 一次只改一个变量，改完用**同一口径**复测，记录新旧数值。
- 没有提升就回滚，不要留着「看起来更快」的复杂度。
- 提升明显才做第二处；连续两处没效果说明定位错了，回第 2 步。

## 5 常见高性价比改法

- 把 IO、解析、建连挪出循环；能批量的别单条发。
- 缓存结果，但必须写清失效条件与上限（无上限缓存等于泄漏）。
- 减少跨边界调用：进程间、JNI、数据库往返。
- 大集合用增量更新替代全量重建。
- 字符串拼接换构建器；热路径减少临时对象。

## 收尾

- 留一条可复跑的基准命令或脚本，写明数据规模与期望区间。
- 提交信息里写清改前改后的数字，只写「更快了」等于没写。

出处：基于 obra/superpowers 的调试与验证流程、以及通用性能工程实践改写。
